# Casio Watch Sync — requirements

Requirement identifiers (`R-…`) are cited in the source code comments. "Verified" means confirmed on a real DW-H5600 and a real phone running Sailfish OS 5.2. Items marked "Version 2" are not part of version 1.0.0. Numbers that do not appear have been retired.

## 1. Scope

- **R-GEN-1** Version 1 does two things: (a) periodic time sync of Casio Bluetooth watches, (b) forwarding of phone notifications to the watch. Nothing else. The time comes from the phone's own clock (R-TIME-12).
- **R-GEN-2** Time sync is the base function and is available for all supported Casio BT watches; notification forwarding is secondary.
- **R-GEN-3** Support is declared per model in a model table (name pattern, protocol family, per-model parameters such as the day-of-week encoding). Only models tested on hardware are marked "supported"; the others are "untested" and shown as such in the UI. Only the DW-H5600 has been verified. Watches of the GB-6900 family use a different GATT layout.
- **R-GEN-4** Version 2 (out of scope for version 1): activity data (steps, heart rate, SpO2, …) with an exportable archive on the phone.
- **R-GEN-5** A user may own several watches. The app keeps a list of the paired Bluetooth devices whose name matches the model table. Each entry has an alias the user can edit (stored by the app; the Bluetooth alias is not touched), a silhouette picture, the model and its support status, enabled or disabled, last sync and last error. The list can be reordered; there is no maximum number of watches. Connections are never simultaneous: sessions run one after another in list order. The notification profile (enabled apps, blacklist) is single and shared by all watches. Time sync runs for every enabled watch, each with its own back-off and result (R-TIME-9). Alert notifications (R-NOTIF-10) go to every enabled watch; the link-status notification (R-NOTIF-11) is written per watch, in that watch's session. Models not marked tested can be enabled by the user at their own risk, after confirming a warning. A watch that is out of range must not hold up the others, so each connection attempt has a short timeout. Not tested with two watches.
- **R-GEN-6** *Version 2.* For a watch whose model is not marked tested, a compatibility wizard (about 5 minutes) lets the user save an anonymised log to send to the developer. The app sends nothing by itself. Steps: (1) connect, check the GATT layout and read the name (`0x23`) and version (`0x20`); (2) write the current time and ask whether the watch shows it correctly; (3) send one test notification with the alert flag and ask whether it arrived, vibrated and sounded; (4) summary. The log is a readable text file on the phone: model name, app and Sailfish OS versions, GATT UUIDs, the answers to features `0x23`, `0x20`, `0x13` and `0x10` as bytes with every address removed (in particular bytes 1–6 of `0x10`, which hold the watch's own BLE address), timings, MTU and the user's answers. It contains no Bluetooth address, no alias, no phone identifier and no notification content other than the fixed test text.
- **R-GEN-7** Version 2 also covers in-app management of the other watch features: basic settings (`0x13`: time format, operating sounds, auto light, language, …), alarms (`0x15`/`0x16`), time zone, DST and world cities (`0x1d`/`0x1e`/`0x1f`), reminders (`0x30`/`0x31`). Every write must be validated before sending, since the watch discards malformed frames silently (R-TIME-6), and the previous value kept so it can be restored. The watch applies DST changes by itself (observed).
- **R-GEN-8** The application is English only in version 1. Strings are marked for translation from the start (`qsTr()`/`tr()`) so that translations can be added without code changes.

## 2. Time sync

- **R-TIME-1** The app periodically sets the watch time from the phone's own clock. The accuracy of the watch therefore equals that of the phone clock, which comes from the system date and time settings; the app does not check it.
- **R-TIME-2, R-TIME-3, R-TIME-3a, R-TIME-3b, R-TIME-13** Withdrawn (external time sources are not used; see R-TIME-12).
- **R-TIME-4** The app does not modify the phone clock; it writes the phone's current time to the watch.
- **R-TIME-5** Precision target: ±1 s relative to the phone clock at the moment of writing. The time frame has 1 s resolution and the round trip on the vendor channel is 0.15–0.2 s (verified).
- **R-TIME-6** *Verified.* Time frame: feature `0x09`, 11 bytes `09 | year LE(2) | month | day | hour | minute | second | dow | 00 | 01`, written to `26eb002d` after `StartNotify` on it. The watch silently discards malformed frames, so the app validates every field before sending.
- **R-TIME-7** *Verified.* On the DW-H5600 the day-of-week byte is ignored: the watch derives the weekday from the date (tested on a Sunday with the byte set to 0, 7 and 3; the watch showed Sunday each time). The app writes Sunday=0 … Saturday=6 and does not depend on it for this model; the byte stays a per-model parameter because other models may use it. Not verified: other models, and a date whose weekday contradicts the byte.
- **R-TIME-8** *Verified.* The watch never reconnects by itself for a sync; every connection is started by the phone (`Device1.Connect`, 0.4–1.3 s with no discovery running) and lasts a fixed ≈46 s. A sync is: connect, write, let the connection drop, within one session.
- **R-TIME-9** Sync once a day by default; the interval is chosen from a fixed list: 6 h, 12 h, 24 h (default), 2 days, 7 days, 2 weeks, 30 days. If the watch is out of range or the connection fails, retry with back-off and show the last successful sync time; never retry in a tight loop.
- **R-TIME-10** Identify the watch by name pattern and/or service `26eb000d`, never by a stored address alone (the BlueZ object and address changed once during testing). The model comes from the name (`Device1.Name`, not the editable `Alias`) and is confirmed at the first connection by feature `0x23` (returns `CASIO DW-H5600`) and by the service. Several watches of the same model have the same name, so the key of a watch in the settings is the address of the paired device; at the first connection feature `0x10` is read and the watch's own BLE address (bytes 1–6, reversed) is stored as a check, so that a changed BlueZ address with the same name and the same `0x10` address is recognised as the same watch. Not tested with two watches.
- **R-TIME-11** Do not run LE discovery while connecting (a connect with discovery on took ≈51 s, without it ≈1 s; cause not isolated).
- **R-TIME-12** The only time provider is the phone's own clock. No choice, no backup, no list. The app makes no network access at all, needs no Internet permission and has no consent dialog.

## 3. Notification forwarding

- **R-NOTIF-1** The app obtains the list of applications that publish notifications and lets the user choose which are forwarded. Only apps enabled by the user forward notifications. Apps discovered from the `app_name` of seen notifications are listed but disabled by default. The user can remove an app from the list; it is re-inserted (disabled) only if a new notification from it arrives. A blacklist holds applications that are never forwarded and never shown in the list: a case-insensitive substring of `app_name` (no wildcards, no regular expressions), editable in the UI, empty by default; it wins over an enabled app; empty entries are ignored. The app's own notifications are always dropped. The watch category of a forwarded notification comes from a fixed table `app_name` → category with default 0 (generic); the table ships empty.
- **R-NOTIF-2** The documented Sailfish API does not allow reading other applications' notifications: `Nemo.Notifications` only publishes and closes the app's own notifications, and the notification service (`org.freedesktop.Notifications`, session bus) is documented for sending only.
- **R-NOTIF-3** *Verified.* An unsandboxed ordinary process of the user can monitor all notifications via `BecomeMonitor` on the session bus. Inside a Sailjail sandbox this is denied (`AccessDenied`, also for legacy eavesdropping), while publishing still works. The component that reads other apps' notifications therefore cannot run in a sandboxed (Harbour-compliant) process (R-PLAT-6).
- **R-NOTIF-4** Forwarding is opt-in per application (default off) and the user can see what is sent. Notification text leaves the phone for the watch, so the content is limited to sender, title and message.
- **R-NOTIF-5** *Verified.* Watch channel: characteristic `26eb0030`, write-without-response, every byte of the frame inverted; a 22-byte header (id u32 LE, delete flag, alert flag, category, 15-character timestamp) followed by sender, title, subtitle and message, each with a 2-byte LE length. The alert flag makes the notification pop up immediately; without it the notification goes to the list only. Delete = same id with delete flag `0x02`.
- **R-NOTIF-6** *Verified.* The detail view on the watch scrolls, so there is no display line budget; the list row shows about 12–13 characters of `sender / title`. UTF-8 accented letters and € render. The frame must fit the MTU: 214 bytes were accepted, 286 refused.
- **R-NOTIF-9** *Verified.* Establishing a connection empties the watch's notification list, so every session (also a time sync) wipes what was there. Keeping notifications on the watch is therefore not a feature; the feature is the timeliness of the alert (R-NOTIF-10). There is no "clear all" command.
- **R-NOTIF-10** *Verified.* Every forwarded notification is sent with the alert flag set: the watch pops it up at once, vibrates and sounds, unless sound and vibration are disabled in the watch settings. There is no silent mode and no per-app alert choice.
- **R-NOTIF-11** The app keeps one automatic silent notification on the watch showing the date and time of the last remote operation (the last correct connection with the phone: a time sync or the forwarding of an alert). It is sent with the alert flag clear (list only); the watch shows the date and time taken from the frame timestamp. The sender is `CWS` (Casio Watch Sync) and the title is always `Sync`, because the list row shows only about 12–13 characters; the message starts with `Casio Watch Sync`, then `Last contact with phone` and, when alerts were sent, the app name of the newest one; category 0. It is written in the same session as the operation: after the time frame for a sync, and before the alert notification so that the alert is the newest entry. Since each connection empties the list, it is rewritten at every session. If this write fails the session counts as failed. The phone-side resident notification shows the same time.

## 4. Platform and distribution

- **R-PLAT-1** Target: Sailfish OS 5.x, aarch64. The whole app is outside Harbour: sandbox disabled (`Sandboxing=Disabled` in the desktop file), because the notification reader cannot run in a Sailjail sandbox (R-NOTIF-3).
- **R-PLAT-2** Harbour's API restrictions (for example QtBluetooth being excluded) do not constrain the app. The BLE client uses BlueZ over D-Bus (`org.bluez`).
- **R-PLAT-3** *Verified.* A GATT client (connect, write, enable notifications) works unsandboxed on the phone through `org.bluez`.
- **R-PLAT-5** Licence: GPL-3.0-or-later. No code was copied from other projects (see `reverse-engineering.md`).
- **R-PLAT-6** The whole app is non-Harbour. Package and app name: `sfos-casio-sync`. Title shown to the user: Casio Watch Sync, abbreviated CWS. Distribution: GitHub (source and built RPM releases, aarch64). Release RPMs are signed with GPG; the signature and the public key are published with each release. The README states that the app is outside Harbour and the Jolla Store, and that it reads all notifications.
